# 界面与缓存

以下是 2026-10-17 实装观察，控件位置与名称可能变化。先读当前电脑/浏览器能力的文档，获取新快照，再按实际控件操作。默认使用用户指定的原 Space、原聊天和正确 bot。

用户明确要求独立 Space 时，按授权新建同一目标的专用空间，后续固定复用，切勿共享控制造成冲突。空间安排仍保留原聊天、原 Dot 和原 bot/群聊参与方，不以新聊天替代验收。

## 安全输入和例程回读

收到用户覆盖的批量接入授权后，可由受托 agent 代填安全控件，记录真实执行者，不逐 bot 重问，也不把代填记成用户亲手输入。实际平台另有本人确认要求时，给出具体原因和需确认的原会话；不把一次应用门槛推广为所有密钥都必须本人输入。

1. 记录目标显示名、平台 UUID 和例程。切换 bot 后，先确认实际选中标题与 UUID。原生应用可能短时显示上一聊天的可访问性树，必须等到目标标题出现才读配置或输入。
2. 由目标 bot 提供绑定唯一变量名的安全密钥卡，例如 SWE 使用 `GROK_BRIDGE_KEY_SWE`，Tibo 使用 `GROK_BRIDGE_KEY_TIBO`，原始黑布丁使用 `GROK_BRIDGE_KEY_BLACK_PUDDING`。原始 bot 同样只读本方变量，无通用 fallback。早期浏览器曾出现 password input，placeholder 类似“在此粘贴您的 GROK_BRIDGE_KEY”，以及表单提交按钮；该历史通用标签不能用来确认当前变量隔离。依据当前语义定位并核对实际保存变量，不固定像素坐标。
3. 在控制工具内部从明确私密文件读取该 bot 对应 key，直接填入本方唯一变量的 password 控件并提交。已有正确原 key 可以改存，无需重生成。不在工具参数明文拼接 key，不打印变量值、原始页面树、截图或发送含 key 的聊天；只读取本 bot secret。
4. 保存后重新读取目标标题、实际变量名和“密钥 已保存”状态。不同 bot 可自定义字段标签，不能只按一个英文标签判断未保存。已保存控件通常无法读出原值，首次运行须从实际 helper runtime 只计算并比对预期 SHA256，匹配后才发送，再检查响应 sender。保存状态、唯一变量名与指纹预检分别记录；唯一变量名本身未验证系统隔离。
5. 从原生 Grok 例程的安全配置面板读取 Webhook URL、Webhook 密钥和 Authorization 标头，先核对当前 bot/例程，再写入对应私密配置。输出仅保留匹配结果。

同步回读该 bot 的 helper 与原例程，确认两处固定引用同一本方变量。常规完整请求显式 end_of_turn=true，只有尚有后续片段时才使用 false；检查实际请求载荷，避免完整请求使对方一直等待。

实装中网页把“Webhook URL”等显示为普通文本，原生应用中的同名按钮才能打开安全面板。例程列表出现“无法加载”或短暂为空时，应换已授权的原生观察方式核对，不能据此宣布例程不存在。右键“编辑”曾仅把编辑文字放入聊天草稿，不能把草稿当成配置已保存。

不要把全量 AX/DOM 原始结果发到日志。密钥面板用不自动展示的读取模式，在控制运行时内筛选白名单状态。交还用户前收起密钥面板和未提交草稿。

## 自动审核规则

先检查被拦的具体动作。已授权桥内任务可限定为本实例固定 HTTPS443 域名、允许的消息路径、作用域回调、已登记 bot、各自已保存 key 及用户任务范围，保留内置审核和其他用户规则。

作用域规则需要同时覆盖被动 callback 和主动 /messages；只允许一次 final=true 回复会破坏多轮协作。不要让规则自动允许任意 URL、任意本地命令或文件公开分享。若请求自行追加 anyone-with-link、公开上传或覆盖他人文件，删掉这些未授权动作，重新核对实际请求。

规则保存后重新打开逐字回读。若审核器仍拒绝且无法在授权范围内缩小动作，记录具体拦截理由并向用户说明，不通过改写身份或提示绕过。

## 公共入口更换后的连接与 trigger

实装时当前 UI 无法编辑旧 ChatGPT 插件 URL，需要以新 `/mcp` 地址建立连接并复用原 OAuth client。保留原 Dot 与原接收 task，先按 [部署迁移](deployment.md) 确认授权、无在途/未知消息和一致备份，再停用旧 source 并替换同一 task 的 trigger。新连接不带来新增并行 receiver 的需要。

新 source 的 trigger 使用宿主生成的身份。提交替换时省略旧 source 的 `trigger.id` 和旧 SID，不把旧值复制到新 source。保存后用 list 回读原 task 的 source、trigger 和新 SID，并核对服务端新 SID 的持久绑定；按钮或保存成功只是一层结果。需要变更 binding 时走同一 owner/Dot 的受控单次迁移，不把清空 binding 当默认步骤。主机迁移也要回读 bot helper、原 routine 主机校验和自动审核规则，旧 callback 不自动换域名。

## 三层工具缓存

分别核对下面三层，才能定位“服务已更新，Dot 仍按旧工具执行”。

| 层 | 核对内容 |
| --- | --- |
| 服务端 tools/list | 当前运行代码、send_message 的 recipient/task_id/parent_task_id/delegation_id 等字段及描述全文 |
| 插件账户目录 | 当前目录的字段与 send_message 描述全文是否和服务端一致 |
| 原始 Dot 运行时 | Dot 实际可调用的工具参数、send_message 描述全文和当前接收任务规则 |

字段一致还需核对 send_message 描述全文，确认它分别解释了换方回复与同方分段续发。既有会话 reply_to 始终指最新消息；同方续发引用自己的上一条 end_of_turn=false 出站 MID，不 claim 自己消息。只看到新增字段、刷新成功或描述片段，尚未完成新描述加载的验收。

只修发生陈旧的层。服务目录正确而插件账户目录陈旧时，刷新现有插件目录；字段与描述全文已一致时跳过这步，不重建账户。若只有原 Dot 运行工具仍旧，先核对并收口当前在途轮次，确认原 Dot 空闲后暂停并恢复同一个 Dot；检查恢复成功，不能只凭按钮点击。让原 Dot 回读实际字段与描述全文，再核对原接收任务允许的 sender 范围和当前已核对的订阅。

若旧工具使在途轮次无法处理，先保存受影响 CID/MID 和实际执行状态，协调该任务的恢复。外部执行或用户操作状态不明时保留阻塞，不重复派活；确认这些工作已收口后再恢复原 Dot。不能通过新建替代账户或代 claim/complete 避开这个依赖。

若 Dot 已看到新字段与新描述全文却拒绝执行，按其实际拒绝原因处理，不继续当缓存问题反复刷新。若用户在控制浏览器、原会话正在工作或存在活跃桥消息，交还或等待，避免刷新中断。

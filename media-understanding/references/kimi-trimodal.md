# Kimi MiniMax-M3 密集逐帧三合一

任务：联合逐帧视觉、音频和文字时间戳理解视频。这个分支增加拆帧密度，并用 Kimi Code
内置 AgentSwarm 做三个独立的完整观察，不把三人分成只能看到某一轨的三个角色。

## 输入和输出

- 输入：当前用户指定的视频绝对路径；原件只读，不扫描邻居媒体。
- 默认输出：视频所在目录的 `frames_<视频文件名去掉扩展名>/`，例如 `clip.mp4` →
  `frames_clip/`。这是该分支明确允许的同目录输出，调用方无需再补一句 output-dir。
- 输出目录必须新建，遇到同名已有目录不能覆盖或删除；可通过 `--output-dir` 指定另一个
  确切目录。不要把这个目录冲突扩大成项目占用或 writer claim。
- 普通 Kimi 视频/Swarm 与旧 direct 路线保持不变。只在用户选择三合一时执行本分支。

## 执行命令

```bash
python3 <skill-root>/scripts/providers/kimi_trimodal.py --input <absolute-video> --execute
```

默认 `MiniMax-M3`、3 个观察者、每秒 2 帧。可显式调整 `--observers N`、`--fps`、
`--prompt-file`、`--config`、`--asr-model`；不擅自降低密度、只取关键帧或换模型。
不传 `--execute` 时只完成本地预处理。准备脚本通过 ffmpeg 做确定性导出，模型分析
实际交给 Kimi 内置 ReadMediaFile、Read 与 AgentSwarm，不让模型猜文件处理是否成功。

1. 探测源视频、记录 SHA-256/时长/音视频流。帧按每 0.5 秒时间轴输出原尺寸 JPEG，
   文件位于 `images/`；`frames.json` 记录帧 ID、时间戳、路径与 hash。
2. 导出 `audio.wav`（PCM，保持原采样率和声道）；同时生成640×320、3fps 黑画面 AAC 的
   `audio-carrier.mp4`，供当前 MiniMax 视频兼容音频实验路径读取。
3. 用已经安装的本地 Whisper 与已有模型生成词级时间戳 JSON、SRT/其他文本输出。
   默认只读 `~/.cache/whisper/base.pt`，也可显式传模型路径；不得偷偷下载模型。
   缺依赖时报告本地缺项，不把 ASR 丢掉后继续宣称三合一。数字全零音轨直接记录
   `digital_silence` 与空字幕，不强行生成文字；没有音轨则记录 `no_audio_stream`。
4. `timestamped-transcript.json` 保存文字层及音频来源。ASR 是候选转写，空结果表示
   本次未识别出语音，不等于证明没有声音；自动语言猜测不能当成音频事实。
5. Kimi 主 Agent 通过一次 AgentSwarm 创建 3 个新上下文。三人收到同一个完整 manifest
   和问题，只有观察者编号不同；每人读全部图像、音频载体、时间戳文字，不互读报告。
   鼓励一轮发出多个媒体读取以降低往返；这不包括并列发出多个 AgentSwarm。禁止把拼图或选帧摘要冒充全量读取。
6. 主 Agent 汇总三份原始报告，保留帧 ID/时间/音频或 ASR 来源、独有发现、冲突与未知。
   使用中文输出；附各人的实际覆盖帧数、音频读取情况、ASR 状态。

多视频：当前 `kimi_trimodal.py` 一次接收一个 `--input`。在同一个父 Agent 中处理多个视频时，
为每段视频保留自己的 `frames_<视频名>` 和报告，等待前一轮完整返回后再运行下一轮。
原生 CLI 也可把“视频×观察者”合并为单个 Swarm 的多个 items；每项绑定该视频的完整帧集、
音频载体与转写，按视频汇总。详见 [Swarm 调度与多视频任务](kimi-readmedia.md#swarm-调度与多视频任务)。
不要把多个媒体读取可并行误解成同一步可并列调用多个 Swarm。

## 能力和容量边界

MiniMax-M3 的独立原生音频输入未获当前官方合同证明，Kimi ReadMediaFile 不直接接受 WAV。
2026-09-15 的 Kimi 0.43.0 / M3 实测中，640×320 载体调用成功，但模型报告只能看到黑画面，无法判断声音。
用户随后说明该录屏可能原本就没有声音。因此该样本不足以评估听音能力，既不能判通过，
也不能判失败或认定能力未实现。需用含已知清晰语音/声响的样本单独验证；当前保持 Unknown。
音频载体是已显式选用的实验方式；黑画面不是原视频画面，音轨被装入视频也不证明
模型听懂。观察者必须区分“从图像看见”“ASR 转写写着”“实际听到且可核对”。不能以
字幕推断音色、噪声、音乐或录音质量，声音能力未证实时标 Unknown。

每秒2帧会漏掉短于0.5秒的瞬态；逐帧表示读取全部已导出的2fps帧，不是读取原视频30/60fps
的每个编码帧。保留密度与原尺寸会增大上下文和费用；这个 runner 是有界的单组执行。
长视频超过容量时需按连续时间窗口规划三观察者任务并汇总全段，不能悄悄跳帧或循环压缩
丢弃材料；当前脚本不自动完成跨窗口批处理。

## 验收

`preparation.json`、`frames.json`、`audio-info.json`、转写原始输出及组合 manifest
分别证明准备阶段。`analysis/verification.json` 检查每人是否精确读取全部媒体和
指定文本、独立上下文人数、模型及工具结果；所有帧/音频/文字的 hash 必须保持不变。
CLI 退出0不等于全量覆盖，更不等于语义正确。原始 `*-report.md` 与 wire 记录保留。
发生 provider/模型步骤错误时停止，保留已读数量和缺失项，不报告三合一完成。

参数和模块依据：[Kimi 分支合同](kimi-readmedia.md)、[音频合同](audio-understanding.md)、
[OpenAI Whisper](https://github.com/openai/whisper)。时间戳是 ASR 的估计，不冒充人工逐词校准。

## 兼容性修复记录

2026-09-15：64×64/1fps 黑画面载体在单独读取和混合读取中均触发 MiniMax HTTP 400 /
2013；改成既有音频实验路线的 640×320/3fps 后单独读取通过。两种编码同时变化，
只能把问题定位到载体编码组合，不能宣布确定的最小尺寸或帧率限制。该 3fps 仅用于
人工黑画面载体，真实画面导出仍为 2fps。保留失败记录，不复用旧输出目录重发。

2026-09-15 完整素材复测：Kimi 0.43.0，34.4秒原视频导出69帧；修正载体后 315.49秒完成。
一次内置 AgentSwarm 建立3个独立上下文，每人精确成功读69张图片、1个音频载体、1份转写，
主 Agent 完成汇总；实际 native wire 的10项调用检查全部通过。ASR为空，三人将听音标为
Unknown，故这是全量逐帧/转写/Swarm调用通过，**不是原生听音或整体语义质量通过**。

抽查仍发现三人把应用内 Space 卡片界面共同误称为操作系统窗口管理功能，并把页脚地区、
远控横幅等普通现象列为“异常”。最终指引补充：依据可见名称或已给身份命名产品/功能；
缺少身份时沿用画面原标签；没有预期行为与偏差证据，不主动寻找 bug。该措辞改进仅完成
静态检查，未再付费重跑，不声称已经消除共同误判。三人一致仍需主 Agent 对关键帧复核。

调用方完成后读取 `analysis/main-report.md` 与 `analysis/verification.json` 再回复用户。
按“画面事件与帧ID/时间 → ASR与声音层 → 分歧/未知 → 实际覆盖”汇总；原始报告不覆盖。
输出载体成功、工具全读、语义正确与真正听音是四个独立结论。

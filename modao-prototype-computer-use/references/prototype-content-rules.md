# 原型内容规则

这是原型生成与修改的设计约束，和鼠标键盘操作步骤同样适用。来源分为用户明确纠正与本次归纳；最新用户要求优先，不能把官方示例或历史截图当成用户认可。

## 用户明确纠正

| 规则 | 适用范围 | 具体执行 |
|---|---|---|
| 按要求绘制交互状态页面 | 用户只要求画原型、补状态页的任务 | 画出编辑、输入、结果、错误和成功等需要的状态；不擅自做运行时计算 |
| 结果标题应是业务名 | 本次计算公式结果与同类合计区 | 标题用“合计（元）”，分别修改标题和提示；组件类型名无需一起改 |
| 运算符应准确并居中 | 本次公式编辑器和键盘 | 符号与数字逐个核对字符、水平与垂直对齐。本次用 `+ - × / ( )`；不以破折号或 emoji 代替 |
| 有自动计算说明时，不加“只读”标签 | 合计结果区已经有“自动计算数值”或下方自动展示/计算说明的 PC、移动页面 | 删除或不添加额外“只读”徽标/文案，保持必要标题、结果及说明即可 |

最新原话：

> “只读”属于 AI 味，你有下面的描述自动计算之类的，就不需要提示“只读”了。
> 这些属于原型生成的规则，不是操作细节，但也需要通过 skill 进行规范。

这项纠正指产品画面的文案，不撤销资料读取、工具权限或文件写入边界中的只读约束，也不要求把真实可编辑与不可编辑行为混为一谈。

## 哪里必须补备注

这是日常原型设计的完整性要求，适用于新建、完善原型及补备注任务，不以高经考点为前提。对本次涉及的页面和流程主动检查：**仅凭画面及原型中就近可见的说明，执行者能否明确知道如何实现、使用和验收？会影响这些判断、但画面没有表达清楚的规则，必须补备注。** 题面或需求文档已经写过，也要把适用规则带回对应原型位置；不因“已给信息”“不计分”省略。用户只要求局部改字、仅回答等窄任务时，仍遵守该范围，不顺带改全稿。

按当前任务要求的业务对象和流程检查下表，既包括已画出的部分，也包括需求已要求但原型漏画的部分。不因清单出现某类项目就凭空新增功能：

| 需要检查的位置 | 画面未清楚表达时需补的内容 |
|---|---|
| 字段、输入框、选项及列表列 | 取值来源、默认值、必填或条件必填、单位/格式/精度、允许范围、唯一性、可编辑条件、字段联动及校验反馈 |
| 按钮、链接及操作菜单 | 触发条件、作用对象、单条或所选批量范围、结果和去向、确认/取消语义，以及对相关数据的影响 |
| 状态、角色及流程节点 | 谁在什么状态能做什么、状态如何变化、完成后的下一步；多个状态同屏或混合选中时怎样处理 |
| 计算值、汇总、自动编号及关联数据 | 计算或生成口径、数据来源、更新时机、空值/舍入处理、关联字段变化后的影响；不只放一个示例结果 |
| 搜索、筛选、排序、分页及选择 | 生效范围、默认规则、条件组合和重置行为，以及翻页或切换条件后选择是否保留 |
| 弹窗、跨页跳转、保存及返回 | 带入/带回什么、何时生效、取消或返回是否保留未保存内容、与原页数据的关系 |
| 当前流程实际可能出现的空、失败、冲突和边界状态 | 无数据、校验失败、重复操作、批量部分成功等如何反馈及继续；只补当前业务适用的状态 |
| 已有打印、导出及其他输出 | 输出范围、字段口径、格式和分页等与屏幕不同但实现必须知道的要求 |

备注写清具体对象、适用条件、规则与结果；按需要补边界和依据，不机械套齐所有字段。按钮已写“新增”不必再贴“点击可新增”的同义备注，但创建后的默认状态、去向或特殊限制不清楚时必须说明。可见状态页表达画面，备注解释画面背后的规则；二者不能互相代替，也不要求为每条备注配置可运行交互。

### 先读全相关说明

判断缺漏前，检查本次对象的卡片、打点正文及相关状态页。打点只有编号或正文未展开时，记为未读；相关页已有说明时核对适用范围和能否定位，再决定补引用、补差异还是新增备注。此要求适用于 Ego 和 Computer Use，读取方法服从当前工具能力。仅调研时记录缺口，不改页面。

### 继承旧稿的依据

| 旧稿信息 | 如何使用 |
|---|---|
| 多处出现的表达与页面组织方式 | 可作首稿参考，按 [旧稿复用与备注表达](reuse-and-note-writing.md) 使用；当前用户纠正优先 |
| 工具通用能力或渲染组件类型 | 用于定位功能；实际复制方式、母版关系和可编辑性仍需在当前界面确认 |
| 角色、金额、单位、公式等业务规则 | 绑定所属项目、对象和状态，不带入另一项目 |
| 有明确适用范围的阶段裁剪 | 保留该范围；后续完善按当前要求处理，不扩成永久禁令 |
| 名称残留、内容冲突、空白或没看到的说明 | 查相关页和批注后判断；原因不明就保留未知，不据此归纳用户不需要这项设计 |

日期帮助追溯变更，不能单凭较新日期判定已获确认或整张旧卡作废。核对同一对象的明确修改内容，只替换被覆盖的条款，保留仍有效的部分。授权修订时同步相关状态页；若旧稿受到保护，报告具体冲突位置和未修项。颜色、作者栏或截图数量都不能证明确认状态；新增待决备注仍按当前警示样式执行。

### 主动补全与真实缺口

- 用户、题面、附件或现有一致规则已经明确的内容，直接整理成对应位置的备注，不重复问用户；检查原型是否已把这些内容表达清楚。
- 当前材料足以推导、不涉及新增业务决策的缺失说明，主动补齐，必要时写明推导依据。表达、布局等常规设计判断由执行者完成，不全部转成待确认问题。
- 影响行为但确实没有依据或材料冲突的决策，在对应位置写明具体缺口及影响，使用待确认样式；可以给建议方案，但明确是建议，不能把猜测写成已确认规则。继续完成不依赖该决策的部分。
- 一个规则跨多个页面时，可用明确标注适用范围的共用备注，并在各使用处给出清楚可定位的引用；页面独有的差异就地说明。不能只写“见需求文档”让使用者自行寻找，也不要复制多份易漂移的长文。

制作前检查涉及的页面、动作和主要状态，区分“画面已表达 / 需要备注补全 / 确有待决问题 / 不适用”；可在已有任务计划或交付说明中简要记录，不强制另造表格或评分文件。交付前沿主要操作路径回看，确认必要规则在原型内可找到、彼此一致。发现必要备注遗漏应补齐；真实未决项明确报告，不能用卡片数量或考点覆盖率宣称完整。

## 先判断原型要补什么，再判断能不能考

当前需求、用户最新决定、现有原型分别核对。按当前需求逐项检查原型，补齐缺少的功能表达，并核对页面上的实际控件。

| 情况 | 原型应如何处理 | 与考点的关系 |
|---|---|---|
| 需求明确，原型已有对象但缺解释 | 就近补必要备注，核对相关状态和示例 | 已给信息也要补；是否新增计分另判 |
| 需求明确，原型漏了对应对象或状态 | 当前任务是完善原型时补上所需页面、控件或状态及备注；仅允许备注时标明具体缺页/缺控件，不假装已实现 | 不能用“原答案没有”否定需求，也不能只为出题增加需求 |
| 当前流程存在，材料未写常规设计细节 | 在当前目标内主动完成合理的呈现、反馈、返回等设计，并说明选择；涉及业务决策时给建议及待决项 | 合理设计方案不自动成为唯一标准答案 |
| 现有字段或功能的业务政策确实未定 | 就地说明具体待决问题、影响与建议；可保持多种合理方案，不要求先取得唯一答案才留备注 | 按业务设计需要补充备注 |
| 旧备注、数据或状态与当前需求冲突 | 授权完善的范围内修正；用户当前明确禁止修改旧内容时指出原位置的冲突及未修项，避免新旧规则同时看似有效 | 修复后读回原型中的实际结果 |
| 与目标无关的新角色、日志、流程等扩展 | 不擅自加入；有价值时作为范围外建议说明 | 不编进答案后再拿它扣分 |

“补全/完善原型”包含其范围内必要状态、说明和一致性修正，无需用户逐个点名遗漏。“只补备注”限定修改对象，不免除受影响页面的新旧备注缺陷处理，按 [发现问题必须处理](annotation-layout.md#发现问题必须处理) 执行。当前用户明确的“旧内容不改”“仅回答”等限制仍约束该次操作；历史派工中的这类限制不能变成以后任务的默认禁令。静态原型无需配置真实公式、数据库或运行时事件，但计算口径、输入输出、状态转换和异常处理仍要用页面或备注讲清楚。

备注写给使用、实现和评审原型的人：对象、条件、动作、结果要具体。避免“需有交代”“重新核对相关资料”等空话，写清哪些字段如何变化。评分用的“缺少则不通过”、难度、权重和模型表现留在 rubric，不能进入产品备注；业务本身的“校验不通过时提示……”则是必要规则。

若当前任务已经分工，内容计划先覆盖所有必要原型项，再另外筛选考点。备注允许没有考点编号，关联字段留空或用空列表；二者不要求数量相等或逐条对应。执行者发现遗漏、冲突或错误前提，应带具体位置返回内容负责人修订，不能以“计划外”“不计分”静默跳过，也不能自行突破已分配的写入范围。负责人跟进原型修订及回读，不能只验收文字与计划一致。

## 用户的原型布局与组件规则

以下是用户明确要求的原型设计规则，适用于不同原型工具，不是墨刀操作技巧。工具步骤只负责实现这些规则，不能以工具默认布局取代设计判断。

- **节约空间，紧凑而不拥挤**：备注靠近说明对象，保留阅读和区分所需间隙。不把卡片放得过远制造长引线，也不为压缩画布把备注挤进狭窄页间空隙。
- **引线不交叉，尽量短直**：空间充足时采用直接连接，不做无必要的折线或绕行；“已经连对目标”不能豁免路径检查。调整布局后确有障碍或拥挤才允许必要的少量转折，交叉仍不通过。
- **拥挤时调整整个目标画布的页面排布**：将页面及其备注作为布局单元，移动相邻页面、调整行列或页间距，释放足够空间，再把卡片就近排开。不能只挪备注、缩字或加折线来迁就过窄的页间距，也不能把所有页面拉得很远。保持页面内容、名称、流程顺序和连接对应关系；尊重用户明确固定的页面。
- **能用一个组件就不拆两个**：矩形本身能输入文字，并满足本次样式与交互要求时，直接在矩形内编辑文字，不另叠“矩形框＋文字”两个组件。仅在组件确实不能满足所需能力时才组合，并说明具体原因；不因此重建未涉及的旧页面。

制作及验收按 [备注布局与连线](annotation-layout.md) 执行；其中涉及的移动、选中和文字编辑方式按当前工具处理。

业务流程图另按 [流程图设计与检查](flowchart-design.md) 处理节点、条件分支和流程箭头。备注引线用于指明说明对象，流程箭头用于表达业务去向，检查时分别核对其含义；页内拥挤可加长页面或改纵向排列，页面外拥挤再调整相邻页间距。

## 新增备注与考点的范围检查

原型设计先按本文件判断完整性，考点只在用户要求评测时另读 [原型与考点分开处理](assessment-boundary.md)。该文件约束评分资格，不限制已授权的原型设计补全。不能因一条内容已在题面出现、不适合计分或没有关联考点，就从备注中删除。

## 需求状态、文案与交互范围

每条需求区分用户已确认、材料有依据但尚缺决策、助手提出的建议。用户现场修改与最新答复优先于旧草稿，保留原话及覆盖关系。不能把新增假设写成“需医院/业务方确认”；原型能展示的交互也不自动成为已确认需求。

确实未决的备注按 [布局合同](annotation-layout.md) 使用警示色并局部加粗；确认后及时改文案和状态，并按 [本期改动的颜色](annotation-layout.md#本期改动的颜色) 保留本期标记。颜色用于区分版本改动，需求和开发状态另按实际记录。产品备注写动作、条件与结果，删除“本页演示”“不代表生产权限”等无助于实现的过程说明；中文文案遵从当前写作要求，业务依据与文字润色分别检查。

一次简单配置能在一个弹窗完成时，优先复用既有控件完成选择、必要核对与保存；不因存在多种组件就增加分步向导、审批或未要求字段。用户要求多步流程时遵从具体业务。矩形等原生组件已支持所需文字、边框和对齐时，直接复用一个组件，按上面的组件规则检查；不因此全量替换现有布局。

项目专属的角色权限、字段顺序、固定比例、数据上限及空间标识只在对应任务生效，不从历史案例带入其他项目。普通页面和打印视图的同名字段分别验证，不将某一视图的格式当成全局规则。

## 可复用的设计归纳

以下是由上述纠正归纳的实施判断，不冒充用户逐字原话：

- 文案只帮助使用者理解业务、完成动作或处理错误。不要把实现状态、内部组件属性、模型工作过程当成产品内容。
- 已有标题、默认提示或辅助说明表达同一信息时，先判断是否重复；无需通过多个徽标反复解释自动计算。
- 保持参考 UI 的语言、密度和层级。结果字段的背景与数值足以表达状态时，不额外添加技术说明。
- 示例数据与错误文案保持上下文一致。示例金额是静态展示，不据此添加公式、填入测试企业真实业务数据或宣称运算已验证。
- 继承原 UI 时同时继承有效规则，并去掉用户已经指出的问题；视觉还原不是机械保留缺陷。

## 检查例子

| 画面 | 判断 |
|---|---|
| “合计（元）” + 输入区“自动计算数值” + 下方自动计算说明，再加“只读” | 多余提示，去掉“只读” |
| “合计（元）” + 金额/自动计算提示，沿用原结果区颜色 | 满足本项纠正；其他页面要求继续检查 |
| 用“计算公式”作为结果业务标题，只在旁边写“合计” | 标题改错位置；直接改业务标题 |
| 表达式区域画出“单价 × 数量”，页面没有数据来源 | 可以是静态示意；不应自动进入公式配置 |
| 后续用户明确要求显示锁定状态并提供对应参考 | 按该任务实际需要处理，不能把合计案例扩大成禁止所有状态说明 |
